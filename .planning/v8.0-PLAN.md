# v8.0 Implementation Plan — Production SaaS Foundation

## Milestone Goal

Prepare Jobot for a private hosted beta for individual job seekers by locking product boundaries, proving tenant isolation, enabling safe hosted persistence, and defining the operational gates required before any real-user release.

This plan is intentionally executable under provisional assumptions. It identifies the work to do before public beta launch while preserving the current self-hosted path as a supported parallel mode.

## Workstream 1: Product and Policy Contract (Phase 19)

### Objective

Set the business and policy envelope for the beta so engineering decisions are not made in a vacuum.

### Decision Areas

- customer segment: individual job seekers first, no employer or team workspaces yet
- initial geography: single-market private beta or limited geography pilot
- pricing model: private beta likely free, with paid launch deferred until retention and AI costs are validated
- AI provider model: hosted managed provider or user-owned keys remains deferred until policy review
- source access policy: explicit allowed-source matrix for LinkedIn, Google Jobs, StepStone, and others
- data processing and retention policy: what is stored, how long it stays, and who can export or delete it
- support ownership: internal owner, escalation path, hours, and response expectations
- risk posture: no public launch without explicit go/no-go approval

### Execution Tasks

- document the exact beta user persona, usage flow, and success criteria
- lock the initial feature scope and explicitly mark out-of-scope items
- create the source-policy matrix and allowed-source list
- define cost and usage guardrails for AI inference and storage
- capture privacy disclosures and a support escalation model
- document the private-beta launch gate and no-go triggers

### Exit Criteria

- all policy decisions are either final or explicitly labeled deferred with an owner and risk note
- the engineering team has a single source of truth for beta scope and no additional SaaS assumptions are treated as fact

## Workstream 2: Tenant Isolation, Privacy, and Hosted Security (Phase 20)

### Objective

Prove that user data remains isolated and access is fail-closed before hosted workflows are built on top of that model.

### Technical Requirements

- inventory every data surface with ownership: profiles, jobs, notes, tasks, vectors, caches, exports, logs, backups, provider artifacts
- enforce owner-scoped access in all API routes and all background-consumer paths
- review legacy nullable ownership states and migration rules for historical records
- ensure AI provider calls, storage writes, and task dispatch are all bound to the authenticated user
- add worst-case negative tests for cross-account access and data leakage
- review all sensitive fields that can appear in logs, provider requests, support artifacts, or exports
- define key management, rotation, and encryption boundaries for stored secrets

### Execution Tasks

- complete a data-flow map from user input to provider request to storage and export
- enforce ownership checks in every write path
- add fail-closed behavior when scoped data is missing or mismatched
- implement cross-account regression tests using two or more distinct accounts
- validate that provider and storage secrets are never reflected in UI or logs
- create a privacy review checklist for hosted beta features

### Exit Criteria

- a user cannot read, modify, or remove another user’s data through any route or worker path
- the system records and tests the fail-closed behavior for all sensitive data flows
- the hosted security model is ready for persistence and workflow implementation

## Workstream 3: Hosted Persistence and Runtime Foundation (Phase 21)

### Objective

Move from single-host local patterns to a durable hosted runtime foundation without breaking self-hosted operation.

### Technical Requirements

- select the hosted database architecture and migration strategy
- codify how web, worker, and scheduler roles are separated in production
- implement queue lease and idempotency protections suitable for multiple worker instances
- design hosted/offline storage adapters so local SQLite and hosted PostgreSQL coexist cleanly
- decide whether vector storage stays local, moves to managed vector infrastructure, or remains a hybrid model
- define backup, restore, and rollback procedures for DB and user artifacts
- document how the self-hosted mode remains compatible or intentionally diverges

### Execution Tasks

- audit current DB and vector usage patterns for multi-instance readiness
- create migration and compatibility plan for a hosted state model
- verify task reliability under requeue, retry, and worker restarts
- implement operational health and recovery contracts for the hosted backend
- prepare a restore drill checklist with expected data coverage
- document what remains local-only and what moves into the hosted service boundary

### Exit Criteria

- hosted persistence can survive an app restart, worker restart, or service failure without silent task loss
- the runtime model supports multiple workers and durable queued operations
- production recovery and rollback steps are defined and testable

## Workstream 4: Hosted Personal Workflow and Managed-AI Controls (Phase 22)

### Objective

Deliver the actual user-facing private-beta workflow on the secure foundation.

### Feature Requirements

- user onboarding and account creation in the hosted environment
- personal workspace creation and guided first-run flow
- CV profile and job discovery work with clear source indicators
- fit explanations and tracking of applications across a user’s workspace
- editable generated materials and clear approval model
- managed AI quotas with visible remaining budget and reset behavior
- explicit failure states for provider outages or quota exhaustion
- export and delete actions for user-owned artifacts

### Execution Tasks

- add hosted onboarding UX and workspace persistence
- integrate user-scoped job discovery, profile, and fit workflows
- add AI quota tracking, budget display, and fallback behavior tests
- ensure generated outputs remain editable and user-owned
- implement export/deletion flows and retention notices
- validate account-specific source behavior in the hosted environment

### Exit Criteria

- a user can onboard, discover jobs, score them, generate materials, and manage results within a private beta workspace
- the system exposes AI usage and operational limits directly to the user
- harmful silent failures are eliminated by explicit error states

## Workstream 5: Production Gates and Private-Beta Readiness (Phase 23)

### Objective

Turn the built beta into a controlled, operationally safe launch path.

### Operational Requirements

- telemetry for service health, queue health, provider failures, user usage, and cost
- alerting thresholds and support escalation path
- deletion and backup restore test evidence
- retention checks for user data, logs, vectors, and provider artifacts
- incident playbook and rollback plan for hosted failures
- load and cost testing under a realistic private-beta scenario
- measurable beta SLOs and clear no-go conditions

### Execution Tasks

- add observability to core flows and error contracts
- run backup, restore, and retention validation drills
- verify deletion and export coverage across all stores
- test the support, escalation, and incident communication model
- measure AI usage trends against predicted spend and limit budgets
- define the invitation-based go/no-go gate with release owner approval

### Exit Criteria

- the beta is ready for a small, controlled user cohort
- operational readiness is documented and evidence-backed
- the service is not launched publicly without an explicit owner signoff

## Cross-Cutting Constraints

- preserve self-hosted local operation where feasible and note any intentional divergence
- do not treat any research assumption as a final product decision without explicit approval
- no public paid launch before beta retention and AI cost evidence exists
- no user-facing hosted workflow without tenant, privacy, and deletion controls validated
- no broad business commitments beyond the private-beta contract

## Success Criteria for the Milestone

The v8.0 milestone is complete when the private beta contract, hosted security model, runtime foundation, managed-AI policy, and production gates are all validated and documented, and the system is ready for a limited invitation-only beta rather than ambiguous general SaaS rollout.
